## Exact selected meaning and closed tuple

The existing public key phraseKey carries the exact server-issued displayed phrase text. It is not a localization/message key, client lookup enum, action prose, permission, revision or execution grant. No client phrase table or reconstruction is used. Its spelling is exactly `confirm <canonical-action-id-with-each-underscore-replaced-by-hyphen> <32-lowercase-hex-digits>`, with one ASCII space at each separator. The action ID is the exact immutable Preview.actionId from the closed registered public action domain; source-declared action/step IDs do not replace this canonical action ID. This retains the actual nonce-bearing guarded phrase design while giving its v2 field an unambiguous meaning. Full displayed text and submitted text are bounded128UTF8bytes and reject controls/lone surrogates; no normalization, trimming, case folding, localized substitution or auto-correction is permitted.

Confirmation remains exactly {required,id,phraseKey,expiresAt}. If required=false, id/phraseKey/expiresAt are all null. If required=true, all three are nonnull: id is the actual owner-issued mcp-confirmation-UUID within the opaque128byte bound, phraseKey matches the exact current preview action grammar above, and expiresAt uses fixed24UTC spelling already selected by the lifecycle amendment. The expiry is no later than Preview.expiresAt; server expiration uses its actual clock/record, never lexical/client-clock permission. Missing/contradictory/extra keys are denied. The nonce phrase appears only in its authorized original preview/confirmation display, not in generic audit/history/error/log/snapshot/context persistence.

ExecuteRequest keeps the original closed keys. For a required confirmation, confirmationId equals the retained preview id and confirmationResponse is the user's exact entered phrase. The client validates byte equality to the displayed retained phrase before POST but does not prefill, synthesize, automatically accept or derive the response from action/phraseKey. For required=false, confirmationId and confirmationResponse are both null. A tuple mismatch is rejected before any effect. UI Escape only clears local input/stage; it neither consumes nor cancels the remote confirmation.

The independently owned server validates the original durable confirmation record under the common claim/publication owner lock before admitting execution. It binds exact trusted actor/client context, canonical root serviceId, public action and declared action/step where applicable, held definition/registration/generation/modelEpoch, family expectedRevision, original request/candidate/payload/reference identity, targets/effects/plan, expiry, status and correlation. A phrase match alone is insufficient. Existing fingerprints are reused as source components with missing explicit v2 root/revision/candidate relations added in the original durable owner; no second disconnected confirmation queue or body actor authority. Historical records lacking a proved new relation cannot be upgraded from public targets, request labels or client claims; originals remain retained/unavailable or reconciled through genuine original legacy authority.

Claim/consume occurs exactly once within the durable original execution/idempotency transaction. A post-claim reply failure is reconciled by its exact original operation/claim. Recognized replay uses the original record/request/context, never reruns the effect or silently renews confirmation. Expired/stale/used/changed-actor/source/targets/parameters/plan/revision confirmations require a new preview/confirmation or truthful typed uncertain state. Existing error code set is unchanged: confirmation_required for missing/wrong phrase/tuple authority, confirmation_expired for actual expiry, binding_stale/revision_conflict for the actual changed binding, operation_conflict for conflicting claim/idempotency, and source_unavailable/source_corrupt/ownership_unknown for unproven owners. No raw phrase/nonce/private fingerprints in errors.

Fresh prePOST sequence remains cumulative: current exact family readiness/token comparison against the immutable preview, then final fresh trusted connection/context check, then POST. Neither fresh availability nor typed phrase input rewrites original preview targets/effects/token/confirmation. Server independently rechecks all current predicates; client success is not server authority. Confirmation capacity remains64 genuinely pending records with bounded max900second expiry and response/request cumulative limits; live/unresolved claimed records retain original custody rather than being evicted by slicing. Runtime crypto/provider invocation is not authorized by this source amendment.
