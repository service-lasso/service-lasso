# Operator v2 current root lifecycle availability — pending selection

This additive proposal completes the selected immediate prePOST availability requirement with an actual service-scoped route. The five original selected design documents remain byte-identical. No new availability product source may be implemented before parent selection and coherent governance adoption. Source/execution/native/publication gates remain unchanged.

Add `GET /api/operator/v2/services/:id/lifecycle-availability`. It accepts no body or query keys; duplicate/unknown query keys fail closed. URL-decode the ID once, validate the actual portable ServiceId grammar, authenticate the actual ingress actor/client, then enforce general service-lasso:read, current observer-or-higher profile, source disclosure and applicable manifest read permission before source acquisition. Missing/incomplete/uninspectable held discovery is source_unavailable, not positive absence; genuine authoritative complete-roster absence is not_found. No body actor or visible service membership grants admission.

The normal envelope data is exactly `{serviceId,definitionRevision,generation,modelEpoch,capabilities,availability}`. serviceId is the actual canonical requested root. Ready data has nonnull, nonempty opaque bounded definitionRevision/generation/modelEpoch from the genuine current held source and persistent model owner. Unavailable root data retains that canonical serviceId, sets all three binding values null and capabilities to an empty array, and reports the exact closed Availability reason; it does not fabricate revisions or disclose a partial ready roster. Normal canonical timestamp spelling is the actual fixed24-character UTC millisecond Date.toISOString spelling, including .000Z and .120Z.

For a ready root, capabilities contains exactly once each canonical action ID `service_install`, `service_configure`, `service_start`, `service_stop`, `service_restart`, `update_check`, `update_download`, plus `service_reload` as explicit unsupported. Each row uses the original exact Capability schema `{id,availability,requiredProfile,requiredScopes,confirmationPolicy,bindingRequirements}`. Reload is supported=false/available=false/unsupported_capability and has no execute route. The other seven derive requiredProfile, special action scope and confirmationPolicy from the actual guarded policy owner (server durableLifecycleOperationActions1984–1992 and guarded policy196–207), composing general read and every applicable source/manifest entitlement. Five direct lifecycle actions retain unsupported cancellation; update check/download retain their genuine selected cancellation semantics. Cancellation is not an added Capability property.

Readiness is generated from the same real admission/preflight owners used for execution, under a stable current root generation/definition/modelEpoch read. Authorization/profile/source/manifest failure maps to authentication_required or permission_denied only from the corresponding typed enforced owner verdict. Actual dependency blockers, storage failures, held ownership uncertainty, corrupt source and changed binding map to their matching existing closed reason only from typed underlying owner results. Human skippedReason text, capability membership, labels, exceptions or arbitrary diagnostic strings cannot be regex-classified into readiness reasons. Unknown/unclassified owner results are unavailable, retain private originals and require completion of the actual typed producer; they never become available or a guessed known cause.

The current source has genuine no-mutation predicates: lifecycle.running for already-running start; !lifecycle.running for stopped stop; lifecycle.installed for existing install (server3320/3337/3388). These are neither missing source nor dependency failure. Therefore add exactly `no_mutation_required` to the closed AvailabilityReason domain as a non-error business-readiness reason, with legal tuple supported=true/available=false/reasonCode=no_mutation_required. It is an explicit exception to the original error-code-subset wording; the ErrorCode domain is unchanged and no error envelope uses this reason as a code. The source predicate, not its human skippedReason spelling, derives this verdict. Update download uses that reason only when a successfully inspected current update result positively proves no candidate; provider failure/uninspectable metadata or missing required exact digest is source_unavailable. The actual typed update observer must distinguish these states before publication.

bindingRequirements for each ready supported action include definition_revision/runtime_generation/model_epoch; actual provider/artifact/allocation/setup/registry requirements are added only from that same action's concrete enforced immutable plan owner. No optional generic capability list substitutes for an action's required binding. Read root bindings before and after all real preflight observations; a change invalidates the entire ready read and reports binding_stale without mixed-revision data. Expensive external observations share the existing bounded owner deadline and retained unknown cleanup rules. This route does not issue confirmation or a mutation preview and cannot change the original plan's targets/effects/confirmation/expiry/candidate digest.

Immediately before a confirmed POST, TUI rechecks its trusted connection/actor/context and fetches this exact root route. It requires that action's current available verdict and matching original preview root/generation/definition/modelEpoch; unknown/missing/stale/unavailable rows stop the POST and retain the user's draft/preview for deliberate refresh. It never replaces the original preview targets/effects or infers permission from the other rows. The server still independently rechecks every immutable preview/confirmation/actor/source/manifest/owner binding under the actual common publication/operation claim boundary at execute. An availability GET is not a lease or mutation authority. A reply race cannot turn a terminal accepted operation into a fabricated completed result.

The legacy v1 availability route remains authentic and separately labelled compatibility behavior; v2 does not fall back to it or reinterpret its open reasons. Complete Core/TUI codecs and acceptance must cover exact roster/root binding, actor/source/manifest denials, actual no-mutation predicates, fresh prePOST binding changes, unsupported reload, private diagnostics, bounded unknown ownership and unchanged original preview authority.
