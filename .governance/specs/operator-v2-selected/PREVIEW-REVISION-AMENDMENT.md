# Preview expected-revision family amendment — prospective, not adopted

This additive contract does not alter the preserved five selected normative originals, catalog amendment or lifecycle availability amendment. Parent selection and coherent governance adoption are required before new family issuance product code. It repairs a genuine missing authority: existing PreviewRequest/Preview/ExecuteRequest require expectedRevision, but existing family forms do not identify an issuer for that token.

Actual src/server/index.ts preflight: start3321 uses artifactPlan.revision and stableStartContextRevision; stop3338 binds definitionRevision plus stopExecutableRevision; restart3362 binds definition/allocation/runtime/doctor executable revisions; install3389 binds artifact revision; configure3401 binds definition/allocation; setup3425 binds affected definitions and step executable revisions. ## Closed additive wire grammar

Lifecycle availability data adds one mandatory key mutationBindings. Its existing six keys remain exactly as selected. MutationBinding is exactly {actionId,expectedRevision,availability}; actionId is one of the same exact eight lifecycle capability IDs including unsupported reload. mutationBindings is exactly the same complete eight-action roster and order as capabilities on a ready root response; unavailable root response has both arrays empty. expectedRevision is a nonempty opaque control-free string of at most128 UTF8 bytes when this binding availability is true/true/null; otherwise null. Reload always has null expectedRevision and unsupported availability. Each binding has the matching capability's actual authorization constraints; capability readiness alone never grants a revision.

SetupStep adds mandatory expectedRevision:string|null, granting ONLY setup_step_run for that same stepId. Action adds mandatory expectedRevision:string|null, granting ONLY declared_action_run for that same declared actionId. Tokens from another step/action or another family cannot be substituted. Both are tied to the row's actual stepId/actionId, service and definitionRevision. A row granting mutation availability must have nonnull expectedRevision; unavailable rows have null. Existing closed keys otherwise remain unchanged. Setup/action forms with root unavailable return their original empty bounded arrays and no granted revision.

Update-form data adds mandatory expectedRevision:string|null granting ONLY update_install for the same canonical root and actual inspected install candidate. update_check and update_download use their separate exact lifecycle mutationBindings, never UpdateForm.expectedRevision. Removal-form data adds mandatory expectedRevision:string|null granting ONLY service_remove_retain_data for the same canonical root and retainData:true disposition. Available form has nonnull token; unavailable form has null. No candidate absence, literal fallback or unavailable update check is positive candidate mutation authority. Update check remains a real supported operation even when there is no download candidate: its distinct owned policy/source revision can be issued only after the policy/source owner is implemented and positively inspected.

Config preview continues using the actual config-form definitionRevision only because the selected config owner explicitly defines that CAS meaning. Queue preview continues using that exact row's authoritative sourceRevision. Metadata PATCH continues using ServiceMeta.sourceRevision. These three are separate namespaces and cannot substitute for a family mutation token.

PreviewRequest expectedRevision comes only from the same fresh ready family row/binding for the canonical requested root and chosen action/step. Preview echoes it unchanged. ExecuteRequest must equal the immutable retained preview expectedRevision; it never reacquires or overwrites the preview authority. Immediately before confirmed POST, the client obtains the fresh trusted context and exact family binding/form row for the same action/root/step/declared action. It requires both current mutation binding availability and exact token equality with the original preview expectedRevision; a ready capability alone is insufficient. It does not replace the original preview token, targets, effects or confirmation. An expired or stale revision requires a new form/read and preview. Nothing is copied from ServiceSummary, modelEpoch alone or generic availability.

## Genuine private family issuer and recheck

A mutation token identifies one durable bounded private issuance record, not an encoded public path or a hash that alone grants custody. Records bind trusted authenticated actor/client context, canonical root serviceId, exact family and public action ID, declared step/action ID where applicable, original held service registration/definition identity, runtime generation, common all-writer modelEpoch, complete family source roster and its original source revisions, permission/profile/scopes, expiry, issuance identity and consumed/reconciliation state. Token equality is exact; no normalization or guessing. Actor cannot be supplied in a request body. Original private sources and manifests are not publicly disclosed.

An available issuance requires the authentic family owner to inspect its complete required source state under the shared publication lock or stable before/after epoch protocol. Incomplete/uninspectable/corrupt inputs issue no token and retain originals. Issuance records use the existing common durable journal/store extension and bounded retention rather than a second disconnected in-memory authority. Every participating legacy/scheduler/monitor/CLI/startup/materialization writer must advance its actual source revision and common epoch; mutation is unavailable until this relation is implemented for every connected writer. Read-only availability does not claim full delivery.

Family source rosters:
- Lifecycle start/stop/restart/install/configure: actual root/dependency definitions and registration generations, relevant lifecycle/owned process state, actual held provider/executable/stop override/artifact/doctor/allocation/materialization sources selected by the corresponding preflight owner. Bind the exact existing plan components above plus missing held/source revision custody; do not derive effect codes from prose. service_reload remains unsupported.
- Setup: original selected step declaration, guard/rerun/fingerprint/outcome state, affected service/dependency definitions and exact setup executable/materialization/provider input owners. includeManual/force/declared values are request intent captured in preview, never process-custody override. Unsupported declared input schema grants no typed input authority.
- Declared action: exact action declaration/schema/payload policy/declared permission, original executable/provider/materialization/reference owners, trusted runtime generation/allocation/global variable input owners. Input payload/reference is validated and held at preview and bound separately by exact private request/candidate identity; never stored or projected as public form revision text.
- Update: exact root update policy and provider/source metadata owner; download/install additionally bind genuine inspected candidate identity, exact digest/size/artifact and relevant installed/running/rollback state. check is its own source/policy operation. A missing exact candidate digest cannot grant download authority. A rollback uses retained actual preimage and current owner binding, never rebuilt bytes.
- Removal: actual complete held registration/identity-generation-allocation CAS, live owned tree/member absence and dependent roster, every retained/eligible private category and original held object identities. Only the genuine selected removal owner can issue after these exist; no fixture deletion helper, deadline expiry or unknown tree can supply this roster.

Preview verifies the original issuance, same context/action/root, expiry, exact request discriminator and current complete family source relation before constructing an immutable plan. It retains original targets/effects/confirmation and private candidate/reference roots. Execution acquires the same common owner lock, rechecks the exact token record and all original identity/source/epoch/current custody relations before claim/commit/effect. Any intervening writer, source replacement, new dependent, failed inspection, permission loss or unproven recovery rejects with the existing appropriate typed binding_stale/revision_conflict/source_unavailable/source_corrupt/ownership_unknown error; human reason strings are not classified by regex. A recognized completed idempotent operation is reconciled through its original durable claim; it does not become a new execution grant.

## Bounds and acceptance

Ready rosters/rows remain within the existing128 form rows/capabilities and eight lifecycle entries. Revision token bounds count UTF8 bytes and original controls. Existing request64KiB/response256KiB/depth16/8192value/expiry limits remain cumulative including bindings. Duplicate actions/step/action IDs and mismatched root/family/revision availability combinations fail closed at codec and domain admission. Durable private retention is separately bounded by the whole selected store contract and retains unresolved original custody; it cannot evict live claims merely to meet a response budget.

Required source/review coverage includes actual issuers plus all-writer recovery, full closed DTO parity, initial form assignment, prePOST fresh lifecycle readiness without changing preview token/targets/effects, stale/ABA/restart/expired/permission-loss/source-replacement cases, genuine successful family journeys and direct Windows/Linux compiled owners. This amendment is design only: no SOURCE_GO, provider admission, native qualification, execution, publication or final all-46 completion.
