# Core Standalone Runtime

## Intent
Create the first real product spec for `service-lasso` by moving from bootstrap-only governance into an executable core runtime slice. This matters because the repository now has a tracked bounded runtime implementation and needs governed traceability as it widens toward production-ready service orchestration. The first core milestone proved that Service Lasso can run as a standalone manager and consume canonical service manifests directly; the current work under this spec is widening that bounded slice carefully with direct verification.

## Scope
Included in this spec:
- establish the first tracked source tree for the core runtime inside this repo
- define the first bounded standalone runtime slice and its execution boundary
- implement a runnable entrypoint for the core runtime/server
- support canonical `service.json` manifest discovery/parsing for the first runtime slice
- provide direct runnable verification against fixture/sample service definitions
- maintain at least one tracked runnable harness service fixture that can exercise runtime/demo behavior through both API and UI surfaces
- add the minimum build/validation/release plumbing needed to make the core repo behave like a real product repo
- update canonical docs/traceability so implemented behavior is mapped to current runtime behavior

Explicitly out of scope for this spec:
- unbounded parity with external/reference systems
- complete service lifecycle/provider matrix
- production-ready UI/operator features (those belong in `lasso-@serviceadmin`)
- every future manifest normalization decision
- every future runtime provider/integration type
- broad service catalog rollout

## Acceptance Criteria
- `AC-1`: `service-lasso` contains a tracked core runtime source tree instead of being docs/bootstrap-only.
- `AC-2`: A standalone runtime entrypoint can be executed locally and start successfully in a bounded development mode.
- `AC-3`: The runtime can discover and parse canonical `service.json` manifests from a defined service root and report the discovered services reliably.
- `AC-4`: The first runtime slice has direct runnable verification evidence using fixture/sample service definitions, not surrogate-only documentation proof.
- `AC-4A`: The tracked fixture set includes a runnable harness-style sample service that can be started independently and used to exercise API/UI, persistence, and behavior-simulation flows for later runtime supervision work.
- `AC-4B`: The runtime includes one bounded real execution/supervision path that can start, observe, stop, and persist runtime state for a directly executable service definition.
- `AC-4C`: The runtime broadens bounded health support beyond `process` and `http` by directly accepting and evaluating at least one additional manifest health type with runnable verification evidence.
- `AC-4D`: The runtime can optionally wait for bounded startup readiness using manifest health retry fields so start/restart flows can distinguish "process launched" from "service became ready". Canonical `healthchecks[]` readiness aggregates required checks while retaining each required or optional check's id, type, blocking role, outcome, attempt count, and detail across health API, start-trace, dependency-diagnostic, and dashboard/service-detail surfaces.
- `AC-4E`: The runtime supports a bounded manifest-driven `globalenv` propagation model so services can emit shared env values, the runtime can merge them deterministically, and operator/API surfaces can expose the merged shared env.
- `AC-4F`: The runtime owns a bounded port-negotiation slice so manifests can declare desired ports, runtime config/start can resolve collisions deterministically, and operator/API surfaces can expose the assigned ports and resolved URLs.
- `AC-4G`: The runtime supports a bounded install/config materialization slice so manifests can declare service-scoped files to generate, `install` can perform a real preparation step on disk, `config` can render effective runtime config with resolved variables, and lifecycle/state output records what was materialized.
- `AC-4H`: The runtime extends bounded provider-backed execution so at least one provider-managed service can run through its provider path and surface provider/runtime evidence through the API and persisted state. Provider-backed service and setup execution must declare the provider as a dependency and fail closed when that provider, or its release-backed installed artifact, is not ready; direct executables without `execservice` remain an explicit ambient-runtime choice.
- `AC-4I`: The runtime supports a bounded manager-level orchestration slice so `startAll` and `stopAll` can operate across enabled services in deterministic order with explicit skip reasons and direct API proof.
- `AC-4J`: The runtime owns a bounded managed-log slice so supervised processes write stdout/stderr into stable runtime-owned log files, the API exposes real recent log output, and persisted runtime state records the runtime log locations.
- `AC-4J.1`: Log-info, log-read, and log-search accept `type=combined` as an alias for `default`, the builtin combined source id matches the `default` type query, and empty or missing stderr does not fail default/combined reads.
- `AC-4J.2`: Log-read honors advertised declared and discovered service-owned log source ids via `source=` or `type=<sourceId>`, returns empty 200 chunks for missing advertised files, and returns 404 for unknown source ids without treating those ids as invalid builtin types.
- `AC-4K`: The runtime extends bounded orchestration with explicit `reload` and `autostart` semantics so services can opt into startup orchestration, startup can trigger autostart deterministically, and runtime `reload` can rediscover manifests while stopping and restarting previously running eligible services with direct API proof.
- `AC-4L`: The runtime extends bounded observability with explicit per-service runtime-log archival and retention so new managed runs roll forward without unbounded log growth and the logs API can surface retained recent archives deterministically.
- `AC-4M`: The runtime extends bounded observability with explicit process/runtime metrics so persisted runtime state and API/operator surfaces can report launch, termination, duration, and log-count evidence beyond pid/running state without claiming full process-tree telemetry.
- `AC-4N`: The runtime provides one explicit demo-instance quickstart, reset path, and scripted smoke validation flow so a reviewer can exercise the bounded runtime end to end against explicit `servicesRoot` and `workspaceRoot` without manual repo cleanup.
- `AC-4O`: The runtime exposes one bounded consumer-compatibility slice for `lasso-@serviceadmin` so the admin UI can use current runtime metadata, log-read, and core dashboard surfaces without consumer-only hacks.

After a signal has been authorised from verified identity evidence, exit polling may treat only a verifiably absent or zombie process as exited; live identity mismatch or unverifiable evidence remains fail-closed. - `AC-4BJ`: Runtime startup is a durable, recoverable transaction whose preflight, reservation, materialisation, spawn, ownership, owned-readiness, and commit phases can resume or roll back safely after interruption without terminating adopted, unverified, or unrelated processes.

  - `AC-4BJ.2`: A startup failure compensates only resources created by that transaction, stops newly started services in reverse dependency order, releases the transaction's allocation, and terminally seals the journal without terminating adopted, unverified, or unrelated processes.
  - `AC-4BJ.3`: A successful startup proves runtime ownership and bound endpoint reachability for the selected generation before commit, then terminally seals the journal as committed. Once generation commit is durable, interrupted private-preimage cleanup resumes idempotently and can never select resource rollback.
  - `AC-4BJ.4`: A new runtime inspects an interrupted startup before mutation and resumes the same generation only when journal roots, generation authority, workspace and host runtime-instance records, allocation identity, and every recorded service owner agree. Unknown ownership or contradictory generation/instance/allocation evidence remains blocked without PID-only action.
  - `AC-4BJ.5`: When an interrupted transaction cannot resume but every remaining resource is safely attributable, recovery rolls back only the recorded transaction resources, preserves unrelated or pre-existing adopted processes, terminally seals the interrupted journal, and starts a fresh generation with recovery provenance.
  - `AC-4BJ.6`: Startup-generated install, config, and declared setup-output files record bounded private preimages before mutation and public digest/action metadata only after successful writes. Private state is handle-read with pre/post identity and size bounds, transaction temp residue is swept, and Windows sidecars are AES-GCM encrypted under a CurrentUser-DPAPI-wrapped key while restore temps receive a current-user-only ACL. Rollback first quiesces transaction schedulers, then restores or removes a file only when its regular-file path, preimage digest, and transaction postimage still agree; redirected, changed, oversized, undeclared, or unverifiable output evidence remains untouched and blocks rollback. A completed file restoration durably invalidates only transaction-affected install/config flags, generated-file metadata, and declared setup-step success state before a fresh generation. Startup artifact acquisition journals private prior lifecycle evidence and transaction-unique extraction paths before mutation, publishes a verified extraction without replacing pre-existing trees, preserves reusable archive caches, and restores/removes only digest-attributable transaction state; ambiguous, redirected, or modified evidence remains untouched and blocked. Setup log files remain preserved.
  - `AC-4BJ.7`: A successful HTTP or TCP readiness response from a transaction-reserved service endpoint is accepted only when the resolved required target belongs to the transaction allocation, the live listener PID is verified as the transaction-owned service root or one of its verified process-tree members, and the persisted generation/allocation evidence agrees. A target outside the allocation, wrong process, wrong generation, disappeared listener, unverifiable listener, or bounded owner-inspection exhaustion remains fail-closed with a stable redacted classification and never authorizes PID-only termination.
  - `AC-4BJ.8`: The `service-lasso start` baseline install, config, setup, and service-start sequence executes before the owning runtime generation commits, using that generation's journal, endpoint allocation, process ownership, private materialization/artifact evidence, and reverse-order compensation. The CLI publishes a completed baseline result only after the enclosing transaction commits; failure or interruption cannot leave baseline-started processes outside durable recovery ownership, and recovery never stops adopted, unverified, or unrelated processes.
  - `AC-4BJ.9`: A hosted Ubuntu and Windows matrix performs a true subprocess hard exit after every formal durable startup phase: preflight reconciliation, allocation reservation, configuration materialization, process spawn, ownership persistence, owned readiness, and generation commit. Each row proves deterministic resume, attributable rollback, or committed cleanup as appropriate; generation/allocation/runtime-instance/process-ownership agreement after recovery; preservation of verified surviving service owners and unrelated processes; bounded exact cleanup; no secret-bearing public evidence; and no transaction temp or private-sidecar residue.
