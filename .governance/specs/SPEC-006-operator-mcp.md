# Operator MCP

## Intent

Give Cursor and other MCP clients a local-first operator surface on the Service Lasso runtime: inspect services, secret _metadata_, logs, and later guarded lifecycle actions through the same facades Service Admin uses. This spec binds the production MCP programme already tracked as GitHub `#858`–`#864` and the product leftover `#1067`. It does not invent a second MCP server or a second secrets product.

## Scope

Included:

- One MCP adapter in `service-lasso` that reuses runtime/operator facades
- Read-only tools and resources, including secret metadata without values
- A Streamable HTTP identity slice with OAuth protected-resource discovery, scopes, explicit transport modes, cumulative permission profiles, per-actor/client rate limits, and fail-closed server/Audit policy under `#860` / `AC-6C`
- Complete strict read tools and resources under `#861`, guarded lifecycle and maintenance actions under `#862`, followed by long-running operations and release gates
- Documentation in `docs/reference/operator-mcp.md`

Explicitly out of scope:

- A parallel MCP server in Service Admin, Secrets Broker, or work-agents
- Secret values, tokens, cookies, private keys, recovery material, raw env, or KV get/reveal in MCP output
- Generic shell, unrestricted filesystem, raw config documents, or stdin tools
- Guessing a new transport/identity architecture beyond `#858` / `docs/reference/operator-mcp.md`
- Service Admin MCP settings UI (`lasso-serviceadmin#423` is already closed)
- Canonical demo recycle or keep-alive ownership from this spec
- The inherited `#1067` missing SDK-registration baseline defect; `#860` must keep its identity boundary independently testable

## Acceptance Criteria

- `AC-6A`: The read-only MCP prototype exposes a dedicated secret-metadata tool and resource that return allowlisted metadata only: secret refs, namespace/key, assignment/access-policy status, rotation readiness, and Secrets Broker lifecycle availability. Responses, resources, and tests never include secret values, credential sentinels, env values, tokens, cookies, private keys, recovery material, or absolute workspace/manifest/log paths. Live broker lockout counts stay on the existing telemetry bridge until a later slice; this criterion reports lockout as not queried rather than fetching KV.
- `AC-6B`: MCP protocol plumbing uses the supported official TypeScript SDK with stdio and standards-compliant Streamable HTTP (`#859`). This criterion is not satisfied by handwritten JSON-RPC alone.
- `AC-6C`: Streamable HTTP identity, OAuth protected-resource discovery, scopes, explicit disabled/read-only/guarded modes, per-actor/client rate limits, and server-side policy fail closed (`#860`). Observer credentials cannot mutate state. Permission profiles are derived from cumulative granted scopes, actors come from validated identity rather than tool arguments, and MCP execution stops safely when its Audit event cannot be persisted. Local stdio uses an opt-in credential-bearing adapter connected to the active runtime directly, without starting a competing process or looping back over HTTP.
- `AC-6D`: The complete read-only operator surface covers runtime status, paginated services, health, routes, dependencies, bounded redacted logs, Audit search, updates, drift, recovery, and operations, with strict schemas and structured output (`#861`). `#1067` closes only when this criterion plus `AC-6G` meet the product bar for services, secret metadata, and logs.
- `AC-6E`: Guarded lifecycle and maintenance tools call the shared operator/application facade without HTTP loopback or duplicated lifecycle logic; perform metadata-only preflight; enforce the Observer/Operator/Maintainer/Administrator matrix; and require expiring, actor-, target-, parameter-, plan-, candidate-revision-, and single-use server confirmation for risky actions (`#862`). Confirmed plans bind endpoint allocations, manifest definitions, template bytes, resolved service/provider launch files, recursive setup-step, doctor, stop-override and update-hook execution files, and exact SHA-256 artifact/update candidates, then revalidate those bindings at the relevant materialization or immediate pre-spawn boundary. Launch evidence uses the supervisor's exact resolver, including basename and option-file inputs. Update installation rehashes confirmed archive bytes after pre-upgrade hooks and extracts only the verified in-memory bytes; its confirmation states only the stop and hook subprocess effects executable under the chosen force/policy path. Source-safe template admission (`SPEC-002` `AC-4CF.1`, `#1513`) is a separately named guarded mutation: confirmation binds the actor, target service ID, staged digest, immutable template tuple, candidate revision, and declared no-lifecycle effect set; only the reviewed adapter may reuse this confirmation/idempotency/Audit substrate. Exact duplicate idempotency keys are claimed across runtime processes and replay the recorded safe result with truthful replay metadata without repeating mutation, while altered or token-like reuse fails closed. Synchronous completions return bounded resulting lifecycle state. Every allowed, schema-denied, policy-denied, skipped, failed, and replayed attempt writes durable Audit with a safe correlation id; terminal Audit outages retain a recoverable pending outcome rather than repeating a mutation. MCP exposes no generic shell, terminal/stdin, raw filesystem, raw configuration, or secret-value action.
- `AC-6F`: Confirmed long-running install and update actions that do not complete within the bounded MCP request budget return a durable opaque operation id without duplicating the underlying guarded action (`#863`). Operation get/list output is actor- and workspace-scoped by default; only Administrator authority can inspect or cancel another actor's operation. Records survive MCP client disconnect and runtime restart whenever the underlying runtime action survives, and expose only strict status, phase, numeric progress, safe summary, timestamps, allowlisted target ids, correlation id, cancellation support, and terminal outcome. Restart reconciliation reads the persisted guarded execution result; when no authoritative result survives, it records `unknown_after_crash` rather than a false failure. Supported cancellation reaches a deterministic terminal state through the shared facade and records durable Audit; unsupported or too-late cancellation is an explicit non-destructive result. MCP request cancellation is propagated where safe without orphaning or repeating the action. Completed operations have documented bounded retention and cleanup. The domain model stays independent of experimental MCP Tasks so a later Tasks adapter does not change launch behavior. No operation state contains raw command output, logs, secrets, credentials, config bodies, absolute paths, or unbounded error text. `#1465` exposes the same guarded engine through actor/client-scoped Core HTTP lifecycle-operation routes for install, config, start, stop, and restart; availability applies the shared profile-and-scope authorization guard and reports the current safe preflight reason. `#1553` additionally exposes a versioned, read-only reconciliation context on the same validated HTTP read boundary. Core alone derives its opaque instance/workspace and actor/client bindings from the stable runtime lane and validated identity; raw credentials, local-admin/access-token material, JWT payloads, filesystem roots, hostnames, commands and runtime-generation details are neither inputs nor output. The same lane and validated actor/client remain stable through supported credential rotation and restart, while a replacement workspace/lane or changed actor/client produces a different context. The read never changes lifecycle, journal, retained operation, or authorization state, including under concurrent reads. HTTP update-check/download creation and the corresponding supported-cancellation workflow remain an explicit `#1538` implementation gap, rather than an unsupported operation presented as cancellable. The synchronous lifecycle routes stay compatible. Before any durable duplicate lookup or claim, Core validates authorization, normalized action parameters, confirmation identity and phrase, and the complete guarded preflight context. The claim stores `sha256(stableJson(...))` of every immutable governed request binding: action, normalized parameters, confirmation identity and phrase, validated actor/client identity, permission profile and granted scopes, workspace identity, and all preflight plan/context bindings. Actor/client key partitioning remains an outer privacy boundary and cannot substitute for this claim context. Concurrent byte-identical admitted requests replay the one claimed operation before dispatch; any same-key request with altered confirmation or context returns the closed `idempotency_conflict` result, including while the first request remains pending and before the guarded journal exists. To enforce that interval, guarded preflight must consult the actor/client/key durable claim under the operation-state lock when a valid confirmation has an altered phrase, target, plan, or immutable context; it returns `idempotency_conflict` only when that durable claim exists. Missing, malformed, expired, unknown, or otherwise invalid confirmations keep their specific closed validation error. Only the hashed private claim context is persisted or audited. Missing, malformed, or legacy incomplete claim fingerprints fail closed under the shared cross-process operation-state lock. Cross-actor/client requests remain private, stop returns its explicit non-cancellable result, and reload remains unavailable until its shared-facade binding has equivalent evidence.
`#1553` authority custody: Core creates a random versioned noncredential authority only at server initialization under the existing workspace lifecycle lock. Its versioned custody protocol retains three exact records: a staged authority journal, the atomically replaced authority, and the final publication marker. The journal carries only the candidate authority and its digest; it is written before the authority, authority publication is atomic, and the marker is last. A restart rolls forward a missing marker only when the journal and authority both validate and bind the same candidate; a journal-only interruption may materialize that exact staged authority and marker. A valid marker paired with a missing, malformed, legacy, duplicated, redirected, TOCTOU-changed, or custody-mismatched authority fails closed and never rotates. Fresh initialization is allowed only when all three records, the retired v1 pair, and every exact named custody sidecar are absent: crash backups, versioned migration backups, migration journals/candidates, and writer-owned temporary files for the authority, publication journal, publication marker, and retired-v1 records. This inspection is bounded to those protocol filenames and is not a workspace-wide scan. Any matching residue fails closed without creating, replacing, adopting, or deleting authority state. The `GET` route only reads that initialized authority and cannot initialize, reset, rotate, repair, migrate, journal, or otherwise mutate it. It never falls back to paths, URLs, ports, credentials, credential hashes, unverified backups, or secret stores. A supported restart and credential rotation retain one authority; a legitimately fresh Core initialization after a workspace replacement at the same paths and HTTP URL receives a distinct authority. Arbitrary byte-for-byte copies that retain the complete protocol records are explicitly outside this detection claim. Direct server fixtures must await their own initialization settlement before owned workspace deletion; an initialization rejection propagates and never produces a ready state, while failed or unknown initialization retains its workspace. The reconciliation-context `GET` uses the shared MCP authorization-Audit boundary before every success or denial response; Audit persistence failure returns the redacted `mcp_audit_unavailable` result and never discloses actor, client, token, path, raw error, or authorization state. The production appender retains the real persistence context; a test hook receives only a closed redacted Audit projection without workspace roots, credential/token material, raw claims, or paths.

- `#1538` closes the HTTP update gap with only `update_check` and `update_download` on the shared durable-operation route. The route accepts the closed guarded request shape, rejects malformed and duplicate-key JSON before admission, derives profile, scope, confirmation requirement, and cancellation support from server policy, and reuses the actor/client/workspace claim, Audit, recovery, redaction, and cross-process exactly-once contract. A supported cancellation request may acknowledge `cancelling` while the reversible provider request aborts; it reaches `cancelled` only when the guarded action reports cancellation. If a guarded action has already committed a successful result, that authoritative `succeeded` terminal result wins and the cancellation readback is `too_late`; no operation state or Audit record may relabel the committed effect as cancelled. It does not advertise `update_install` or create a second operation engine.
- `AC-6G`: Security, redaction, protocol conformance, packaging, and canonical demo acceptance are blocking product gates in the normal CI/release path (`#864`). The gate drives the supported official MCP Inspector and SDK client against Streamable HTTP, proves the opt-in stdio adapter, initialization/version negotiation/notifications/discovery, closed-world schemas, OAuth identity and transport defences, independent actor/client rate limits, the complete permission/confirmation/idempotency/operation/Audit matrix, deterministic limits, and sensitive-output rejection. A staged package is installed into a fresh consumer root and starts the same MCP server without a source checkout on Windows, Linux, and macOS. Canonical acceptance performs safe discovery and representative reads plus one confirmed exactly-once lifecycle action. Each operating-system lane retains one nonempty, exact-SHA-bound, metadata-only evidence artifact containing supported protocol/SDK/Inspector versions and representative result classifications, with no protocol captures, credentials, raw logs, configuration, environment values, local paths, or secret material.
