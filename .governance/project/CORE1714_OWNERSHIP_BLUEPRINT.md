## 1. Decision and invariants

Recommend **an original native CoreCreator host, per-Core constructor capability, and child-held original Core/creator lifetime handles**, with one private authority roster spanning the whole workspace. The native creator, rather than an arbitrary Node PID or a JavaScript boolean, creates and binds the actual Core invocation. Bootstrap and managed launchers retain observation-only duplicates of that exact Core process object and original creator object. They own cleanup for their own invocation even after Core's death. The target receives neither the Core-owner capability nor the grant channel. A creator-held per-invocation containment Job/cgroup supplies fallback when a launcher itself dies; child-held observation supplies cooperative closure and original failure retention when Core dies.

This deliberately introduces a new native constructor boundary. Current bootstrap and managed code do not implement it. An in-process addon which merely duplicates Node's self handle would bind a process but would not establish authority over its loaded JavaScript, global dependencies or source provider. It is not the recommendation. A native host still needs the actual authenticated installed-source provider described below; its name or executable digest alone cannot authenticate Node's executed source.

Normative invariants:

1. A grant exists only for a native-constructor-created original Core process and one immutable workspace/service/invocation generation. No late `OpenProcess`, PID/path/registry claims, role flag or `authenticated:true` can construct it.
2. No target executes until source/image bindings, original peer enrollment, capability grant and containment assignment are recorded. Owner death or uncertain owner observation closes the run gate.
3. The original object owner records every acquisition, original API result/error/exception, retirement attempt and closure observation before later work. Failed or unknown dependent closure keeps the same actual owner and resources alive; safe independent later releases still run once.
4. Workspace shutdown enumerates every ownership root, including finalizer-only and restart-only records. It never affects another workspace or publishes an internal path-bearing key.
5. A settled Promise, root exit, provisional terminal, empty Job count, successful termination call or closed stdin is not complete process/Job/stream/input/resource closure.
6. Absolute caller deadlines, native inspection policy, original protected assertions and the original eight packaged cleanup attempts are unchanged. A deadline produces failure/unknown, never successful closure.

## 3. Constructor, grantor and authenticated source boundary (N1)

### 3.1 Constructor API and origin

The proposed native `CoreCreator` executable exposes no public mint-from-PID interface. At native constructor startup it holds its own approved installed image, installation directories and authenticated provider configuration, verifies the actual issuer/profile/realm against an independently installed trust policy, and opens a private native ownership roster. A launch request contains a validated transport actor reference, permission/confirmation/idempotency admission reference and approved workspace binding; requests cannot choose native issuer, grantor or ownership objects.

The host uses the approved full Node image and preserves the human's finite N2 decision: full Node22.23.2/full ICU/public library/Buffer/API, complete owned accounting and a measured finite whole-runtime replacement budget for domain0/domain2. The selected choice is recorded in `docs/decisions/NATIVE-RUNTIME-N2-WHOLE-CONTRACT-CHOICE.md` in the parent-supplied CLI source input, subsequent explicit human choice dated 2026-10-05. B0/B2 remain UNKNOWN and Q32 is qualification-only; service1MiB, combined store4MiB and Core128MiB are separate unchanged domains. This proposal supplies neither a numerical replacement cap nor a host exemption/extra pool. The existing Core1643 entire6C architecture remains NO_GO and global T+S remains UNSELECTED.

The constructor must resolve and bind the complete governed Node/Core/native source namespace and actual global T/S dependencies through an authenticated source-authority provider, with original held input custody and dynamic imports/support bytes covered by that route. Those providers are missing, not an implemented “existing” authority. It must not replace the human's decision with an 8 MiB full-Node cap, a Node facade, guessed module list or extension filter. Finite N2 is a budget contract choice, not proof that Node's entire execution graph is authenticated. Missing T/S/global or actual source authority blocks constructor activation before Core creation; this proposal does not select T/S or supersede their whole review.

`ConstructCore(approvedInstalledBinding, workspaceAuthority, admittedActor)` creates the actual Node Core process suspended on Windows and pre-exec gated on Linux, storing its original creation handle/pidfd, immutable kernel birth and held image/source binding. The constructor creates `CoreOwner` only in its native roster: original Core object, original creator object, workspace identity, source binding digest, issuer/profile/realm references, nonce, protocol version and generation. It opens the native Core IPC session bound to this original child, transfers no minting rights to JavaScript, then opens the Core run gate. The actual issuer/profile/realm provider, installation protection and finite source provider are unresolved activation prerequisites, not fictitious values in that record.

The internal Core-facing API is `GrantLaunch(CoreSession, WorkspaceAuthority, ServiceAuthority, admittedPlan)` returning an opaque reference usable only on that session. JavaScript cannot deserialize, clone or rebuild authority; native code performs roster lookup and full context comparison on every call. References are not public service IDs or bearer strings transferable between Core sessions. There is no public constructor accepting an owner PID, signing identity, hash, path or privileged actor flag.

### 3.2 Windows transfer and peer authentication

The native host creates bootstrap suspended from held verified bootstrap image/directories with `bInheritHandles=FALSE`. It stores original process/thread handles immediately. The host's original process handle rights needed for child transfer remain private; peers receive only `SYNCHRONIZE | PROCESS_QUERY_LIMITED_INFORMATION` duplicates of original Core and creator handles. Peers receive no terminate, VM, write, token or duplicate rights on Core. `DuplicateHandle` uses original host-owned Core source handle, original created bootstrap target handle, explicit reduced desired rights, FALSE inheritance and options zero. Never use `DUPLICATE_CLOSE_SOURCE` for grant transfer. The actual returned target-local handle values and original results enter the grant ledger before publication.

A native host-created local named pipe uses first-instance creation, rejects remote clients, enforces the actually configured profile DACL and a closed protocol. Its unpredictable pipe name is a routing address only, never authentication or a public output. The resumed bootstrap can connect before any managed creation, but can do nothing except native enrollment until its peer is validated. Server obtains the OS-reported pipe client PID and token, compares them with the original created bootstrap handle's PID, birth and still-live state, and the configured profile. This uses PID only as a cross-check of an already held original object; it never opens a process from that PID. Server sends the target-local Core/creator duplicate slots and a fresh per-invocation challenge over the validated pipe. Bootstrap compares OS pipe-server identity/token with the received original creator handle, held approved creator image and installed trust policy; a caller-supplied record is not the trust root. Malicious manual bootstrap launch with a spoof issuer or pipe is denied by the installed policy and original peer chain. Both sides record authenticated channel establishment only after these actual checks.

Before managed creation, bootstrap retains the Core/creator observation handles and package locks, asks host to create a native `ManagedPeerGrant` tied to that bootstrap and immutable invocation, creates managed suspended and sends its original child handle to host through the existing authenticated session. Host validates the originally authorized creating peer and original child object before duplication. Handle transfer of that child to host uses the peer's already-held creator process object with only the duplicate right needed for this isolated grant operation; that authority is held only by approved bootstrap, never by Core JS or targets. Host retains original managed process/thread observations and duplicates the Core/creator observation handles into managed with explicit reduced rights/noninheritance. The managed pipe peer is checked against that exact created object before enrollment. Bootstrap does not resume managed until host grant publication is acknowledged; managed then performs its own native source/image/peer checks before target creation.

This avoids transient inheritable Core/creator capabilities in Node or broad handle inheritance into arbitrary concurrent children. For target standard streams only, managed uses `STARTUPINFOEX` with `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, explicit inheritable duplicates of its three approved stream handles and TRUE inheritance, closing temporary duplicates once the original create result is recorded. No owner/grant/Job/image/directory/policy handle is on the target list. All handle-list creation/attribute failures retain original outcomes and deny create; no fallback to inherited-all. General Core child creation is routed through the constructor or explicitly outside this protocol with no cleanup guarantee; a normal entrypoint cannot silently bypass the creator.

Every enrollment challenge includes protocol, original Core/creator/peer birth, workspace native identity, safe service identity, immutable invocation nonce/generation and held source/asset digests. Native grant records and live channel custody authorize enrollment; challenge strings, hashes and paths alone do not. Challenge replay, duplicate grant, foreign generation, unknown slot, extra handles, identity mismatch, incomplete binding and original-owner signal deny admission. Once consumed, a grant cannot be reissued for the same creation under a replacement peer.

### 3.3 Linux construction and transfer

Use original creator-held `clone3(CLONE_PIDFD)` process creation for Core and native launcher peers, with a native pre-exec gate; transfer original Core/creator pidfds and approved input FDs using `SCM_RIGHTS` over creator-held Unix sockets. Use OS `SO_PEERCRED` plus original held pidfd/live birth, configured realm/profile and approved image/source binding. Receive with close-on-exec and exact FD roster/type checks; never reopen by numeric PID. Creator pidfd acquired from its own established constructor authority stays an original lifetime object, not a request field. The target receives only explicitly selected stdio FDs; owner pidfds, grant sockets, locks and cgroup control FDs close on exec.

Containment requires an actually delegated cgroup-v2 subtree per immutable invocation, held directory/control FDs, target gated until membership is committed, and a policy preventing target migration or escape. `cgroup.kill` is the one forced termination issuance; `cgroup.events` populated=0, original target pidfd/reap and all stream closures remain separate observations. Unsupported kernel features/delegation/profile/source provider deny this new protocol; there is no process-group-only success fallback. Existing legacy identity-verified process-group/descendant control remains a separately qualified compatibility route and cannot claim the new owner-death guarantee. `PR_SET_PDEATHSIG` may be supplementary but cannot be the authority: it has creator-thread/registration/exec credential races. Poll the original pidfds and channel; preserve the native owner on unknown. macOS remains Deferred, never PASS or an accidental required fallback.

### 3.4 Prerequisites to activation

Actual installed native issuer, profile, realm IDs, policy provider, grants, actor-to-workspace binding, protected source namespace provider, global T/S dependencies, Node finite N2 measurement, Linux delegation and approved new images are required before constructor admission. These are tracked dependencies under #1714 and existing owning issues, not repeated requests for invented credentials. No source-only document supplies them. An actor already authenticated by HTTP/MCP is necessary for lifecycle authorization but cannot mint a native Core capability. Conversely a native lifetime handle does not grant HTTP/MCP permissions.

### 3.5 Closed native grant protocol

Use a private fixed-width binary header with protocol version1, closed message kind, total frame length, per-direction sequence and invocation generation, followed by the kind's exact closed body. Maximum frame is 4096 bytes; this is a new transport-frame limit only, not a Node/resource budget or native roster limit. Bodies contain bounded opaque roster references, 32-byte cryptographic random challenge, 32-byte source/asset association digests, original peer birth values, closed capability-slot roles and original API outcome fields. Text policy references are at most 128 UTF8 bytes each, validated against the authenticated installed provider's actual exact IDs; public original service IDs use existing manifest validation. No frame carries a path, command, environment, credential, arbitrary JSON or raw exception.

Kinds are `ENROLL`, `GRANT`, `GRANT_ACK`, `BOUND`, `RUN_REQUEST`, `RUN_GRANTED`, `TARGET_ACK`, `STOP_REQUEST`, `STOP_OBSERVED`, `PROVISIONAL_TERMINAL`, `CLOSED` and `DENIED`. Each direction accepts only the kind legal in the exact native state, exactly one challenge response/grant consumption and strictly next sequence. Each role has an exact slot roster (Core observation, creator observation, peer-specific grant channel and approved stream roles). Slots use process-local handle/FD values only after native issuer transfer; a numeric body alone never creates a slot. Reject unknown/duplicate/missing fields/slots, truncation, oversized lengths, wrong state, sequence replay or foreign generation before effect. Preserve original partial read/write/EOF/error and resource outcomes; incomplete frame is unknown/denied, never a synthetic terminal.

Windows OS peer/token/held-original-object checks and Linux original credential/pidfd checks establish the channel before body interpretation can authorize anything. Source authority comes from the actual independently authenticated policy/provider, not these digests/challenges. Run authorization is a one-shot native roster decision; managed still rechecks original owner objects at the execution edge. A host-issued RUN_GRANTED arriving after death cannot reopen the gate. All enrollment/binding/ACK phases use the caller's existing absolute deadline and existing narrower native phase limits; transport framing adds no retry or extended bound. Private provisional terminal cannot authorize JavaScript cleanup until all actual child/socket/listener/stream outcomes are closed and original resource failure policy permits CLOSED.

Windows fallback containment is a creator-owned per-invocation outer Job containing bootstrap/managed/target before their execution gates, with kill-on-last-close and no breakaway. Peers do not inherit/duplicate that outer Job handle. Managed retains its inner target Job; required nested Job compatibility is a direct qualification precondition and unsupported assignment denies before resume. Creator never closes its outer Job on request timeout or while an original owner remains retained. Creator death may kill peers as well as target; that fallback is containment, not proof of successful original finisher retention or stream/input closure after owner loss. Linux creator retains the invocation cgroup; on launcher death while creator lives it issues the shared one cgroup kill. On creator death the surviving child-held original creator observer may issue that same disposition; if all qualified observers are lost, closure remains unqualified rather than inferred from process disappearance.

## 4. Whole authority roster and workspace isolation (N3 / #1576 AC1–AC2)

Create one native-backed `WorkspaceAuthority` from the actual workspace directory identity and trusted runtime context. Canonical paths are private metadata; filesystem aliases/case normalization/reparse changes require held identity comparison, not concatenated strings. Persist one random workspace identity under the owned workspace journal with held-directory validation. Replacement directory or ambiguous aliases deny rehydration. Public service IDs remain the original manifest IDs.

`ServiceAuthority = (WorkspaceAuthority object, original service ID, immutable invocation generation, CoreOwner object, admitted plan)` is an opaque private object. A private structured-key map may index it, but a string matching an existing key is never authorization. Lookup checks all object/context fields before access. No `resolveWorkspaceServiceKey` shortcut accepts a raw internal key. Function signatures receive explicit authority; AsyncLocalStorage may carry convenience context but cannot supply missing authorization, and native callbacks/timers close over the immutable capability.

Core creator host remains alive while any peer resource owner remains retained. Bootstrap stays alive and holds managed image/directories until original managed exit and all bootstrap-owned stream/resource outcomes are known. Managed stays alive on unknown containment or failed input release, with its original file objects, not a copied error summary. Creator death is observed by child-held original creator handles and drives their closure independent of lost IPC. Creator-held per-invocation Job/cgroup fallback covers unexpected bootstrap/managed crash. Its last-handle kill cannot prove closure when the observing owner also died; classify that case unqualified until independent original observers establish target/tree/streams/inputs. No forced owner exit is used to hide retained failures.

A workspace stop closes only its launch gates and target containment, leaving the common Core/creator alive for other workspaces. Core death closes every invocation owned by that exact Core; an unrelated Core/workspace does not share its capability or containment. Within one Core, the whole-stop API lists all its actual workspaces explicitly. Shared physical package directories have independent reference owners; close only each invocation's handles, never delete shared directories as a native cleanup action.

### 5.1 Original wait and status precedence

Wait on original owner/creator/target objects plus control event; capture exact original return immediately. For Windows `WAIT_FAILED`, record immediate original Win32 error; timeout/abandoned/unexpected/unknown never masquerades as object signaled. For simultaneous readiness, inspect original handles without reopening, store each original observation, and apply deterministic event ordering: existing primary failure first; otherwise genuine owner/creator death prevents any new resume/ACK success, while genuine target exit is still preserved as its original code/signal. A natural exit already recorded remains primary; owner death is an additional cause, not invented replacement target status. Normal stop/cancel is a request outcome only; it cannot overwrite an earlier create/wait/native error. Readiness index alone is not a complete simultaneous-state observation.

The once-termination ledger is shared by normal stop, owner monitor, cancelled read/write operations and finisher. Before `TerminateJobObject`, unassigned `TerminateProcess` or Linux `cgroup.kill`, record issuing and retain original API result/error. Other paths await that same issuance; they cannot kill twice. A successful kill call is not an original wait. Original target wait success precedes code query; query failure is preserved. Job/cgroup zero, target closure, reader/drain/stream completion and helper/child closure have separate original fields. Reuse an already-qualified original observation only for its declared object/site, never issue a replacement wait to convert unknown into known.

Native wait/drain threads may keep waiting for genuinely pending operations within owner retention. A completed failed wait/retirement is not retried. JavaScript caller deadline still ends the public request with closed failure; it does not force a retained native owner to dispose resources. During simultaneous exit or lost channel the public result remains unavailable/unknown unless the exact original terminal protocol plus actual child/socket/listener closure is observed.

### 5.2 Resource roster and safe release dependencies

Each acquisition assigns a monotonically increasing private ordinal before later work can throw. Record object identity/alias, acquisition site, original API namespace/status/exception and dependency edges. Pending acquisition stays pending if observation allocation itself fails; never remove it to meet a roster cap. Each release records attempted BEFORE effect; capture immediate original result and retain original exception object strongly. Successful closure clears only that exact original slot. Failed/unknown release keeps it and cannot be retried by another layer or numeric-handle reuse. Exceptions during ledger append/finalizer remain original owned failures and deny successful unwind.
